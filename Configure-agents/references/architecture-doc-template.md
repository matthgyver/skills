# ARCHITECTURE.md template and writing guide

This document is consumed by LLM agents, not humans skimming for the gist. Prioritize density, precision, and groundedness over narrative flow. Every section below is a default - drop sections that don't apply to this codebase, and add ones that do (e.g. "Multi-tenancy model", "Event bus topics") rather than forcing every project into an identical shape.

## Template

```markdown
# Architecture: <project name>

> Generated by analysis on <date>. Reflects the codebase as of commit/state <ref-if-known>.
> Source code is the ground truth - refresh this document when the architecture changes materially.

## 1. Summary

2-4 sentences: what this system does, who/what calls it, and its overall shape (monolith, modular monolith, microservices, library, CLI tool, etc.).

## 2. Tech stack

- Language(s) & version(s): ...
- Framework(s): ...
- Package/build system: ...
- Datastore(s): ...
- Key third-party dependencies that shape the architecture (not an exhaustive dependency list): ...

## 3. System map

List the major components/services/modules and how they relate. Use a short Mermaid diagram if it clarifies relationships (agents can parse Mermaid fine), followed by a plain-text description - don't rely on the diagram alone.

Example:

\`\`\`mermaid
graph LR
  Client --> API[API layer: src/api]
  API --> Service[Service layer: src/services]
  Service --> DB[(Database)]
  Service --> Queue[Job queue]
  Worker[Worker: src/worker] --> Queue
  Worker --> DB
\`\`\`

- **API layer** (`src/api/`): handles HTTP routing and request validation. Delegates to the service layer, holds no business logic itself.
- **Service layer** (`src/services/`): owns business logic. Talks to the DB via `src/repositories/`.
- ...

## 4. Directory guide

A table or list mapping top-level (and notable second-level) directories to their purpose. Keep this to what an agent needs to orient itself - not a full file listing.

| Path | Purpose |
|---|---|
| `src/api/` | HTTP routes and controllers |
| `src/services/` | Business logic |
| `src/repositories/` | Data access layer |
| `migrations/` | DB schema migrations, ordered, never edited after merge |

## 5. Key flows

For each traced flow (see skill Step 2), document it as a numbered sequence of concrete steps with file references. Example:

### Flow: incoming API request
1. Request hits `src/api/routes/orders.ts`, validated against schema in `src/api/schemas/order.ts`.
2. Route calls `OrderService.create()` in `src/services/order-service.ts`.
3. Service persists via `OrderRepository` (`src/repositories/order-repository.ts`), which wraps the ORM.
4. On success, publishes `order.created` event to the queue (`src/events/publisher.ts`).
5. Worker (`src/worker/handlers/order-created.ts`) picks up the event and sends the confirmation email.

## 6. Data model

Key entities and their relationships, at the level of "what an agent needs to know before writing a query or a migration" - not a full schema dump. Note ownership boundaries if multiple services/modules touch the same data.

## 7. External integrations

Third-party APIs/services this codebase talks to, where the integration code lives, and any non-obvious auth/rate-limit/retry behavior baked in.

## 8. Conventions

Patterns that are consistent across the codebase and that new code should follow: error handling, logging, naming, testing patterns, dependency injection style, etc. State them as rules, not observations ("errors are always wrapped in `AppError` before crossing a layer boundary", not "the code seems to often wrap errors").

## 9. Invariants and gotchas

The non-obvious things that are easy to break. This is often the highest-value section for an agent. Examples:
- "Never write directly to `users_legacy` - it's read-only, replaced by `users` as of migration 0042."
- "The `config/` files are environment-specific and templated at deploy time - don't hardcode values that look like they belong there."
- "Circular import risk between `src/services` and `src/events` - always import event types, never event handlers, from services."

## 10. Build, run, test

Exact commands, verified against the actual manifest/scripts - not generic guesses.

- Install: `...`
- Run locally: `...`
- Run tests: `...`
- Lint/format: `...`
- Build/deploy: `...`

## 11. Open questions / areas of uncertainty

If parts of the codebase were ambiguous or you couldn't fully verify a claim by tracing code, say so explicitly here rather than presenting a guess as fact. This is more useful to a future agent than false confidence.
```

## Writing guidance

- **Cite real paths.** Every architectural claim should be traceable to a file or directory. If you can't point to where something lives, either go find it or flag it as uncertain - don't state it as fact from framework conventions alone.
- **Prefer lists and tables to paragraphs.** Agents parse structure faster and more reliably than prose.
- **Skip padding.** No "In today's fast-moving software landscape..." - the summary section should read like an internal engineering doc, not a blog intro.
- **Size it to the codebase.** A small CLI tool doesn't need all 11 sections at length; a multi-service backend might need more than one system map. Compress or expand accordingly.
